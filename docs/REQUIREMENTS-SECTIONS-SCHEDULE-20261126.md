## 一、背景与目标

现有内容按「主题」组织，首页只有类型、平台、标签筛选，没有稳定的内容板块。随着内容从「中小学教育、AI、科技前沿」扩展到 **0–18 岁全年龄段**，需要先把板块体系定下来，再提供一个独立的「采集设置页」，让板块和定时采集可配置、可观察、可开关。

本需求要解决三件事：

1. **板块可配置**：新增「婴幼儿养护（0–3 岁）」「学前教育（3–6 岁）」，与现有「中小学教育（6–18 岁）」组成连续的年龄段；AI、科技前沿、工具与效率、人文通识作为全龄兴趣板块。
2. **定时任务可配置**：本机设置页可编辑定时配置，并生成可提交到 Actions 的 cron 片段；公网定时仍由固定 workflow 执行，页面不直接改线上。
3. **自动执行可开关**：公网自动执行由 GitHub Actions 负责；本机 `scheduler.py` 仅作为可选本地模式，默认关闭。设置页用于本机配置和手动采集，不控制线上开关。

**部署形态（方案一）**：GitHub Pages 只做静态展示；GitHub Actions 负责公网定时采集与提交；本机采集服务只用于配置、预览和手动采集，**不部署到 Pages**。

| 角色 | 载体 | 职责 | 是否自动写入 |
|---|---|---|---|
| 展示站 | GitHub Pages | 首页、列表、详情、搜索 | 否 |
| 公网采集 | GitHub Actions `update-data.yml` | 固定 cron 采集、`--verify`、提交数据 | **是，唯一公网写入方** |
| 本机配置台 | `collector/settings.html` + `server.py` | 板块/主题编辑、定时预览、导出 cron、手动采集 | 仅本机手动 |
| 本机调度（可选） | `collector/scheduler.py` | 本机按计划采集，默认关闭 | 仅 Actions 定时停用时才允许 |

**边界**：不引入账号体系、不做云端配置编辑、不接第三方调度平台、不做内容自动审核；采集仍只读公开接口，不登录、不下载、不绕过付费。设置页不进入 Pages 发布产物，公网不应访问到。

## 二、板块体系

### 2.1 一级板块总表

| 顺序 | 板块 ID | 名称 | 年龄段 | 定位 | 初始状态 |
|---:|---|---|---|---|---|
| 1 | `infant-care` | 婴幼儿养护 | 0–3 岁（0–36 月） | 喂养、睡眠、发育、健康护理、居家安全、亲子互动 | 新增，待建主题 |
| 2 | `preschool` | 学前教育 | 3–6 岁（36–72 月） | 入园适应、幼小衔接、早期阅读、游戏化学习、社交情绪 | 新增，待建主题 |
| 3 | `k12` | 中小学教育 | 6–18 岁（72–216 月） | 小学 / 初中 / 高中的学科、启蒙、学习方法 | 沿用现有 4 个单元 |
| 4 | `ai` | AI 与智能工具 | 全龄 | 大模型、Agent、AI 开发、AI 应用与创作 | 沿用现有 5 个单元 |
| 5 | `tech` | 科技前沿 | 全龄 | 芯片、算力、机器人、航天、新能源、生物科技 | 沿用现有 1 个单元，待补主题 |
| 6 | `tools` | 工具与效率 | 全龄 | 网站、软件、效率方法、实用工具 | 沿用现有 1 个单元 |
| 7 | `humanities` | 人文与通识 | 全龄 | 城市、历史、文化、地理 | 候选板块，暂不强制上首页 |

### 2.2 0–18 岁连续性

年龄段采用**月**做内部单位，区间按 `[age_min_months, age_max_months)` 半开区间，避免边界重复：

| 板块 | 起始 | 结束 | 展示文案 |
|---|---:|---:|---|
| 婴幼儿养护 | 0 | 36 | 0–3 岁 |
| 学前教育 | 36 | 72 | 3–6 岁 |
| 中小学教育 | 72 | 216 | 6–18 岁 |

规则：

- 三个板块必须首尾相接：0–36 / 36–72 / 72–216，不允许空档或重叠。
- 其他板块 `age_min_months` / `age_max_months` 留空，表示「全龄」，不参与连续性校验。
- **覆盖的是分类口径，不是内容量**。新增两个板块只是把 0–18 岁的位置留出来，内容仍要靠主题采集逐步补齐。

### 2.3 板块与单元的关系

- 每个采集单元只能有**一个主板块**；跨板块只在标签/关联里体现，不复制单元。
- 单元新增字段 `section`（板块 ID）；索引从单元文件派生，`metadata` 带上 `section` 与 `section_title`。
- 二级主题仍按现有「采集单元」组织；板块是单元的归属，不替代单元。
- 现有 12 个单元的初步归属（详见上一轮抽取分析）：中小学教育 4 个、AI 5 个、科技前沿 1 个、工具与效率 1 个、人文通识 1 个；婴幼儿养护、学前教育目前为 0 个。

## 三、独立「采集设置」页面

### 3.1 定位与入口

- 页面名称：**采集设置**（不是日常采集表单）。
- 路由：`/collector/settings.html`，与 `collect.html` 并列；采集页顶部增加「采集设置」入口。
- **只在 `127.0.0.1` 本机采集服务中可用；不发布到 GitHub Pages**。`collector/` 必须排除在 Pages 发布产物之外，直接访问线上 `/collector/settings.html` 应为 404。
- 页面职责：配置板块/主题、生成并导出 Actions cron 片段、本机定时与手动采集、查看本机日志；**不控制线上自动执行，也不直接改 GitHub workflow**。
- 线上自动执行、线上数据更新由 GitHub Actions 负责；页面不承担单条/批量采集表单，那仍是 `collect.html` 的职责。

### 3.3 板块配置需求

每个板块可编辑字段：

| 字段 | 类型 | 规则 |
|---|---|---|
| `id` | 文本 | 创建后不可改；`[a-z0-9-]`，全局唯一；系统保留的三个年龄段板块不可删 |
| `title` | 文本 | 必填，2–12 字 |
| `age_min_months` / `age_max_months` | 整数 | 系统保留的三个年龄段板块必填且必须连续；其他板块必须留空（全龄） |
| `order` | 整数 | 决定首页/页内顺序；提供上移/下移 |
| `enabled` | 开关 | 关闭后不在首页展示，但历史数据保留 |
| `description` | 文本 | 选填，一句话说明板块边界，最多 60 字 |

操作：

- 预设 7 个板块均可改名、排序、启停；`infant-care`、`preschool`、`k12` 为保留年龄段板块，不可删除。
- 新增板块：只允许新增「全龄」自定义板块，默认 `enabled=true`；不能设置年龄段，也不能插入 0–3 / 3–6 / 6–18 三段之间。
- 删除板块：只能删除「自定义且无单元」的板块；有单元的板块只能停用，避免数据失去归属。
- 每个板块显示：单元数、最近采集时间、启用/停用状态、主题数。

#### 板块下的主题（v1 最小配置）

点击板块展开主题列表，至少支持「新增 / 编辑 / 停用」，否则新增板块无法参与自动采集：

| 字段 | 规则 |
|---|---|
| `topic_id` | 自动生成或按标题派生，创建后不可改；与现有单元 ID 兼容 |
| `title` | 必须；显示标题 |
| `must_keywords` | 必须；1–4 个限定词，全部命中（AND）；不要放同义词 |
| `any_keywords` | 选填；0–5 个同义词/近义词，任一命中（OR）；为空时只按 `must_keywords` 匹配 |
| `channels` | B站 / 公众号 / 小红书，至少选一个，默认 B站 |
| `enabled` | 停用后不参与自动执行，历史数据保留 |

匹配规则为**混合模式**：`must_keywords` 全部命中，且 `any_keywords` 至少命中一个（若填写）。v1 不支持排除词和复杂匹配，`exclude` 放 v2。新增板块若要参与公网 Actions 采集或本机自动采集，必须先有至少一个启用主题。

示例：`must_keywords: ["婴幼儿", "喂养"]`，`any_keywords: ["辅食", "母乳", "配方奶"]`。标题/简介必须同时出现“婴幼儿”和“喂养”，再出现任一喂养方式才收录。

### 3.4 定时任务配置需求

#### 公网定时（GitHub Actions，固定）

- 来源是 `.github/workflows/update-data.yml` 里的 `schedule`，页面只读展示当前 cron 与北京时间的换算结果。
- v1 公网只采用**一个统一时间槽**（默认 `23:00 UTC` = 北京 `07:00`），每次运行全部启用主题；暂不支持不同板块在不同时间跑。后续若要做分板块时间，需要 workflow 多 cron + `group` 参数，放 P2。
- 页面修改的是「本机定时」，可一键生成 cron 片段；用户复制到 workflow 并提交后，线上才生效。页面不直接改线上文件。
- 手动补跑：页面提供 GitHub Actions 的 `workflow_dispatch` 入口链接，不代用户触发。

#### 本机定时（`scheduler.py`，可选）

- 全局默认 `off`；只有把 Actions 的 `schedule` 停用后，才允许打开本机自动执行。
- 每个板块可设置：
  - `auto_enabled`：是否参与本机自动执行；
  - `frequency`：每天 / 每周 / 手动（v1 不做每月）；
  - `weekdays`：每周模式下多选周一–周日；
  - `run_at`：`HH:MM`，北京时间；
  - `stagger_minutes`：可选 0–59 分钟错峰；
  - `pages`：本次搜索页数，默认 3，范围 1–10；
  - `max_new`：单次最多新增多少条，默认 5。
- 页面显示本机「下次运行」，并注明「仅本机调度生效，不影响线上」。
- 公网「下次运行」只显示计划时间，并提示 GitHub Actions 可能延迟，不承诺准点。

#### 导出 Actions cron

- 北京时间转 UTC：`UTC = 北京 - 8 小时`；跨日要顺带减一天。
- 示例：北京每天 `07:00` → `0 23 * * *`；北京周日 `07:30` → `30 23 * * 6`（UTC 周六晚上）。
- 导出前校验时间格式、星期选择；导出片段只含 `schedule:`，不覆盖 workflow 其他内容。

#### 执行边界

- 「立即执行」只对本机采集生效，执行前二次确认；正在跑时按钮禁用。
- 线上立即执行走 GitHub Actions 手动触发，不在设置页内执行。
- 同一时间只允许一个本机采集任务运行；后到的任务标记为「跳过，已有任务运行中」。

### 3.5 自动执行与状态

- **公网**：由 GitHub Actions `schedule` 自动执行；设置页不控制线上开关，也不拉取 Actions 实时状态，只展示当前 cron 和跳转链接。
- **本机（可选）**：`scheduler.py` 默认关闭；开启时由它按本机定时串行执行，设置页显示本机心跳与日志。
- 状态字段（本机）：`idle / running / success / failed / skipped / missed`；保留最近一次与最近 30 次摘要。
- 失败重试：单主题失败重试 1 次，仍失败则记录并继续下一个主题；**部分成功也要落盘并可提交**，不能因一个主题失败丢掉整批成功数据；Actions 侧同样要求“部分成功也提交”。
- 公网错过：GitHub Actions 的 cron 可能延迟或被跳过，不做自动补跑；需要时用 `workflow_dispatch` 手动补跑。
- 本机错过：`scheduler.py` 离线期间不批量补跑，启动后只对 30 分钟内到期任务补跑一次，其余标记 `missed`。
- 日志：本机页面展示尾部 100 行；线上运行日志在 GitHub Actions 页面查看。

### 3.6 保存、校验与冲突

保存前校验：

1. 板块 ID 唯一、合法；名称非空；
2. 0–18 三段连续、无重叠；自定义板块必须全龄，不得设置年龄段；
3. 启用的板块至少有一个启用主题，且主题的 `must_keywords` 不为空；新增板块需先在页内建主题；
4. 本机定时时间格式合法，每周模式至少选一天；导出的 cron 必须通过 UTC 换算校验；
5. 本机自动执行开启时，必须检测到 `scheduler.py` 心跳，且检测到 Actions `schedule` 已停用；任一不满足则拒绝开启；
6. 配置写入采用「临时文件 + 原子替换」，写入前留快照；写入失败不改变旧配置。

冲突规则：

- **GitHub Actions 是公网唯一自动写入方**；本机 `scheduler.py` 默认关闭，只在 Actions `schedule` 停用时才允许打开。
- 设置页读取 workflow 文件，发现 `schedule` 仍存在时，本机自动执行开关置灰并提示「线上定时正在运行」；页面不直接改 workflow。
- 线上配置变更（板块、主题、cron）必须提交到仓库后才生效；页面保存的只是本机配置。
- 配置保存时若有本机采集正在运行，允许保存，但新配置从下一次本机调度开始生效；本次运行沿用启动时的快照。

### 3.7 权限与安全

- 仅 `127.0.0.1` 可访问；不提供公网登录模式，也不把 `collector/` 发布到 Pages。
- 页面不放 GitHub token、不直接调 GitHub API；配置变更由用户自行 review 后提交。
- 所有配置写操作二次确认；删除/停用板块、修改定时、立即执行都要有明确提示。
- 婴幼儿养护内容涉及健康科普，页面与内容页需标注「公开科普信息聚合，不替代医生诊断/治疗」。

### 3.8 数据同步推送 Git

设置页增加「同步推送数据」能力：把**本机采集产生的数据变更**提交并推送到 GitHub，供 Pages / Actions 使用。只推数据，不推代码、配置、文档。

**推送范围（白名单）**

- `assets/data/collections/*.js`（新增/修改的采集单元）
- `assets/data/index.js`（重建后的索引）
- 其他文件一律不进入本次提交；代码、`sections.yml`、`topics.yml`、workflow、docs 都排除。

**页面入口**

- 布局底部增加「数据同步 Git」区：显示当前分支、待推送文件数/单元数、远端是否领先、最近一次推送结果。
- 按钮：`预览变更`、`同步推送数据`；无数据变更时禁用；推送中显示进度与日志。
- 推送成功后显示 commit hash、推送文件数、远端分支；失败显示原因与下一步操作。

**前置检查（任一不通过则阻止推送）**

1. 当前仓库在 `main` 分支，且没有进行中的 merge/rebase/cherry-pick；
2. 没有本机采集或另一个 Git 同步任务在运行；
3. `assets/data/**` 存在实际变更；
4. `python3 collector/generate.py --verify` 通过；
5. `git fetch origin main` 成功，且 `origin/main` 是本地 HEAD 的祖先（远端没有领先提交）；
6. 本地 Git 凭据已配置、远端可访问；日志中的远端 URL 必须脱敏。

**提交与推送流程**

1. 只 `git add` 白名单数据文件，禁止 `git add -A`；
2. 提交信息固定格式：`data: 本机采集同步 YYYY-MM-DD HH:mm（N 单元 / M 条）`；
3. `git -c http.version=HTTP/1.1 push origin main`；网络失败最多自动重试 1 次；
4. 禁止 force push、reset --hard、clean、删除远端分支；
5. 推送被拒（远端已更新）时保留本地提交，提示先 `git pull --rebase` 人工处理，不自动合并；
6. 推送超时后先用 `git ls-remote origin main` 校验远端 HEAD 是否等于本地 HEAD，避免重复提交。

**并发与一致性**

- Git 同步使用独立 `GIT_LOCK`，与采集锁互斥：采集运行中不允许推送，推送中不允许开始新的本机采集。
- GitHub Actions 是公网自动写入方；本机推送是**人工触发的补充写入**。两者可能竞争，靠“fetch 后 fast-forward 校验 + 非快进拒绝 + 不 force”保证不覆盖对方。
- 推送成功后，下一次 Actions 运行会基于新 HEAD 继续采集；页面不保证 Actions 会立即重新部署。

**安全**

- 只能由本机设置页触发；不接受用户自定义命令、仓库路径、分支或提交信息模板。
- 不读取/显示 token；使用本机 Git 凭据（SSH key 或 credential helper）。
- 日志对 remote URL 中的用户名/ token 做脱敏；失败日志保留尾部 100 行供排查。

## 五、后端与调度需求

1. **公网调度（主）**：继续使用 `.github/workflows/update-data.yml` 的 `schedule`，v1 一个统一时间槽跑全部启用主题；采集步骤改为“部分成功也提交”，避免单主题失败导致整批数据不落盘。
2. **本机调度（可选）**：`collector/scheduler.py` 默认关闭，只在 Actions `schedule` 停用时启用；读取本机配置，与现有 `COLLECT_LOCK` / `WRITE_LOCK` 共用采集逻辑，不依赖设置页服务存活。
3. **API（仅本机）**：设置页服务只负责本机配置、状态查询和导出。
   - `GET /api/settings`：板块、主题、本机定时、状态、最近日志；
   - `PUT /api/settings`：校验并原子保存本机配置；
   - `POST /api/scheduler/toggle`：仅本机调度开关；检测到 Actions schedule 时拒绝；
   - `POST /api/run-now`：本机手动执行；
   - `GET /api/actions/export`：生成 Actions cron 片段，不写入 workflow；
   - `GET /api/git/status`：分支、数据变更、远端领先/落后、最近提交；
   - `POST /api/git/preview`：只做检查与变更清单，不提交；
   - `POST /api/git/push`：白名单数据提交并推送，异步返回任务状态；
   - `GET /api/git/job/<id>`：推送进度与脱敏日志。
4. **Pages 发布**：发布产物只包含展示页、`assets/**` 和必要静态资源；必须排除 `collector/**`、`docs/**`、`tests/**`，确保线上访问不到设置页。若继续用分支直出，需要改成 Pages artifact 方式或把 `collector/` 移出发布目录。
5. **数据一致性**：GitHub Actions 是公网唯一自动写入方；本机推送是人工触发的数据补充写入。两端都可能改 `main`，必须靠“fetch 后 fast-forward 校验 + 非快进拒绝 + 不 force”避免覆盖。本机锁无法跨机器约束 Actions，因此推送前要 fetch 再判断，推送被拒时保留本地提交、人工 rebase 后重试。
6. **Git 同步实现**：设置页服务通过固定参数调用本机 `git`，不接收用户传入的仓库路径/分支/命令；只允许 `main` 与数据白名单路径；需要本机预先配置 SSH key 或 credential helper。

**配置生效路径**：本机页面保存配置 → 导出 cron/配置片段 → 人工 review → 提交仓库 → Actions 下次运行读取新配置。页面不做线上一键发布。

## 七、非功能需求

- **可靠性**：公网采集由 Actions 固定 cron 执行；单主题失败不影响整批落盘；配置原子写 + 快照；本机调度默认关闭。
- **性能**：单次 Actions 任务默认 ≤5 个板块、每板块 3–4 页，30 分钟内完成；页面打开不触发采集。
- **数据发布**：Git 同步只提交数据白名单；推送前 fetch + fast-forward 校验；禁止 force push / reset。
- **安全**：设置页仅本机可访问且不进入 Pages 产物；不在页面放 GitHub token；线上设置页应为 404。
- **可观测**：线上看 Actions 日志；本机看页面状态与本地日志；页面能生成 cron 片段。
- **可回退**：配置通过 git 提交可回退；关闭本机调度立即生效；Actions 可停用 workflow；板块停用不删数据。

## 八、验收标准

1. 编辑/排序/停用 7 个预设板块，并新增 1 个全龄自定义板块，保存成功且刷新后仍在；
2. 0–3 / 3–6 / 6–18 三段连续校验通过；制造空档或重叠、给自定义板块设置年龄段时保存被拒绝；
3. 主题配置 `must_keywords` + `any_keywords` 生效：must 全命中且 any 命中一个才收录；只命中 must 不收录；
4. 本机设置「AI 每天 07:00、中小学教育每周日 07:30」后，页面显示本机下次运行正确；导出 cron 为 `0 23 * * *` 与 `30 23 * * 6`；
5. GitHub Actions 按 workflow 的 cron 到点执行，能产生数据提交；页面不声称能控制线上开关；
6. 本机自动执行默认关闭；Actions `schedule` 存在时本机开关置灰；Actions 停用后本机开关可用；
7. 单个主题失败时，其他主题的成功数据仍能落盘并提交（Actions 与本地同一规则）；
8. 本机调度离线错过的任务标记为 `missed`，不会被批量补跑；页面服务停掉不影响 scheduler 已排队任务；
9. Pages 线上直接访问 `/collector/settings.html` 返回 404，设置页只在本机可开；
10. 现有 12 个单元数据不受影响，新增 `section` 字段后 `--verify` 仍为 0 问题；
11. Actions `schedule` 正常运行，`workflow_dispatch` 手动补跑仍可用；
12. 页面在 1280px 与 390px 下无横向溢出；
13. 数据同步预览只列出 `assets/data/collections/*.js` 与 `assets/data/index.js`，代码/配置/文档改动不进入提交；
14. 无数据变更时同步按钮禁用；远端领先时阻止推送并给出 rebase 提示；
15. 推送成功后远端 `main` HEAD 与本地 HEAD 一致；推送失败不 force，超时后通过 `ls-remote` 校验，避免重复提交；
16. 采集运行中同步按钮禁用；同步进行中不能启动新的本机采集。

## 十、风险与已确认决策

| 风险 / 问题 | 说明 | 建议 |
|---|---|---|
| 双调度冲突 | 本机 scheduler 若在 Actions schedule 开启时运行，会互相覆盖数据 | 本机默认关闭；页面检测到 Actions schedule 时置灰本机开关 |
| 设置页误发布 | `collector/settings.html` 若进入 Pages 产物，会被公网访问 | Pages artifact 排除 `collector/**`；验收线上 404 |
| 配置不即时 | 页面只改本机配置，线上要提交仓库才生效 | 页面提供配置 diff / cron 片段；用户 review 后提交 |
| Git 推送竞争 | Actions 可能同时提交，本机推送被拒或覆盖风险 | fetch + fast-forward 校验；非快进拒绝；不 force；保留本地提交 |
| Git 凭据/网络 | 本机凭据缺失、网络失败或超时 | 预检 credential helper / SSH；失败保留提交；`ls-remote` 校验后再重试 |
| Actions 不准点 | GitHub cron 可能延迟；仓库长期无活动可能停用 workflow | 不承诺准点；需要时 `workflow_dispatch` 补跑；定期检查 workflow 状态 |
| 本机调度不常驻 | scheduler.py 停了，页面仍显示本地开关但没执行 | 页面检测心跳；用 launchd/systemd 托管；默认关闭 |
| 关键词误配 | `must` 里放同义词会导致空结果 | 页面提示 must 只放限定词；保存前校验关键词数量与重复 |
| 健康内容合规 | 婴幼儿养护涉及健康建议 | 来源白名单 + 免责声明 + 不用「治疗/根治」表述 |
| 板块可自定义边界 | 自定义板块过多会让首页碎片化 | 系统保留 3 个年龄段板块；自定义只能全龄，需人工启用 |
| 配置页与采集页职责 | 两个页面容易混淆 | 采集页只做单条/批量；设置页只做板块/调度/状态 |

**已确认决策（2026-11-26，v0.4）**

| 项 | 结论 |
|---|---|
| 部署形态 | 方案一：GitHub Pages 展示 + GitHub Actions 公网采集；本机设置页不发布 |
| 公网自动执行 | Actions `schedule` 固定运行，v1 一个统一时间槽；`workflow_dispatch` 手动补跑 |
| 本机调度 | `collector/scheduler.py` 可选，默认关闭；仅在 Actions schedule 停用时允许 |
| 设置页定位 | 仅 `127.0.0.1`；负责板块/主题、本机定时、导出 cron、手动采集、数据推送 Git，不控制线上开关 |
