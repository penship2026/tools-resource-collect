## 一、总体结论

架构方向是对的：纯标准库、零第三方依赖；**采集只写数据、页面是固定模板**的边界守得很干净；数据按采集单元独立成文件，可单独重采、单独下线。文档沉淀（README + WORKLOG + TODO + 两份部署文档）质量明显高于同类小项目。

问题集中在三类：

1. **部署安全**：默认部署方式会把 `.git`、`backups`、源码全部公网可读，且三个写接口无鉴权（实测可复现）。
2. **数据可靠性**：索引与单元文件都是非原子覆盖写，一次异常中断就可能让全站变空白。
3. **工程化**：5 个采集函数近 80 行重复、零测试零 CI、解析器完全依赖对方站点 DOM、存在死参数与死文件；文档口径与仓库实际不一致（声称的 `.github/workflows` 并不存在）。

## 三、P0 详情

### 3.1 按主题采集崩溃：形参遮蔽模块【已修】

原签名 `def collect_topic(..., channels=None)` 与文件顶部 `import platforms as channels`（63 行）同名，函数体内 `channels.platform_name(...)`、`channels.search_topic(...)` 全部指向形参：

```
$ python3 -c "import generate; generate.collect_topic('测试', dry_run=True)"
AttributeError: 'NoneType' object has no attribute 'platform_name'
```

CLI 不传参、Web 端传的是列表，两种入口都会炸——即「按主题采集」主路径在当时的未提交版本里完全不可用。

**处置**：10:09 已把形参改成 `topic_channels`，10:30 复测 `collect_topic(..., dry_run=True)` 不再崩溃。

**遗留建议**：这类「形参与模块同名」的坑一次就够，后续新入口建议用 `channel_list` 之类带后缀的命名，并在 CI 里加一条「所有 CLI 入口 `--dry-run` 冒烟」。

### 3.2 默认部署公开 `.git` / 备份 / 源码【待修】

`server.py` 把项目根作为静态托管根（`Handler.__init__` 的 `directory=ROOT`），`SimpleHTTPRequestHandler.translate_path` 不过滤点目录。实测（默认全功能模式，`python3 collector/server.py 8901`）：

```
/.git/config           → 200  （返回 git 配置全文）
/backups/              → 200  （目录列表，备份 zip 可直接下载）
/collector/generate.py → 200  （源码）
```

同时 `/api/collect`、`/api/toggle`、`/api/title` 无任何鉴权，服务绑定 `0.0.0.0`，而 `DEPLOY.md` 主推方案是「反向代理整体转发 + 可配域名 HTTPS」。等于任何能访问该地址的人都能改站点数据、触发采集、下载整站源码与 git 对象。

**建议**：

- 静态托管加白名单：只放行 `index.html`、`series.html`、`single.html`、`list.html`、`assets/**`（排除 `assets/**` 以外一切）、`collector/collect.html`；拒绝 `.` 开头目录、`backups/`、`docs/`、`*.py`、`.git/`。
- 写接口加 token（Header 或 Cookie）或限制为内网 / Basic Auth；采集页与管理 API 至少要求一个口令。

### 3.3 数据写入非原子【待修】

`write_index`（364-377）与 `write_collection_file`（380-388）均为 `open(path, "w")` 直接覆盖。进程崩溃、磁盘满、容器重启都可能留下半截 `index.js`；而 `load_index` 解析失败只 `print` 一句就 `return []`，表现为 `--list` 为空、`/api/topics` 为空、首页 0 个主题。

**建议**：

1. 两个写函数统一 `写 <path>.tmp` → `os.replace`；
2. 覆盖 `index.js` 前自动留一份快照（复用 `backup_data.py` 的打包逻辑，做成 `snapshot(reason)`）；
3. `load_index` 解析失败时区分「文件不存在」与「文件损坏」，后者明确报错并在 health 接口返回 `index_ok: false`。

## 四、P1 详情

### 4.1 存储型 XSS：index / series / collect 未转义【待修】

`single.html`、`list.html` 都定义了 `esc()` 且用得很规范；但：

- `index.html:227` 起：`'<h3>' + t.title + '</h3>'`、`<img src="' + t.cover + '"`、`tag` 全部裸拼；
- `series.html` 的 `cardHtml`、来源区、标签行：`v.title`、`v.desc`、`topic.source.url` 裸拼；
- `collect.html:585` 起：`${t.title}`、`${t.page}`、`${t.platform}` 裸拼。

标题、简介、封面、标签均来自 B站 / 公众号 / 小红书抓取内容。一篇标题含 `<img src=x onerror=...>` 的文章即可在站点执行脚本；封面 URL 带引号则会直接破坏 DOM。

**建议**：把 `esc()` 提到 `assets/data-loader.js` 共享，5 个页面统一使用（属性值和 URL 也要转义）。

### 4.2 文档与仓库不一致【待修】

- `README.md:45`、`docs/GITHUB-PAGES.md:75,215`：「项目已内置 `.github/workflows/update-data.yml`，提交即生效」——**该目录实际不存在、也未被 git 跟踪**，定时自动采集并没有在跑。
  - 修复成本极低：`GITHUB-PAGES.md:218-269` 已给出完整 YAML，落文件即可。
- 页面数量：`README.md` 标题为「四个页面」，同文件「目录结构」却写「三页面共用的加载器」；`DEPLOY.md:5,118,254` 只列 `index/series/single`，**漏了 `list.html`**——按 DEPLOY 部署静态端的人会得到一个进不去「全部内容页」的站。`WORKLOG.md` 通篇「三页面」也未随 `list.html` 更新。

### 4.3 单线程 HTTPServer【待修】

`ReusableTCPServer` 是 `socketserver.TCPServer`（单线程）。主题采集 30 页 ≈ 30 次搜索请求 + `time.sleep(0.35)`，一次三十秒以上；批量 12 条链接每条 `timeout=25`，恶劣情况数分钟。期间 `/api/health`、页面加载、索引读取全部排队；前端 `fetch` 也没有超时设置。

**建议**：换 `ThreadingHTTPServer` 并给数据写入加文件锁；或把采集改成「提交任务 → 轮询状态」，避免长请求占用连接。

### 4.4 单元身份依赖标题相等【待修】

`collect_topic`、`_collect_article_single`、`collect_batch`、`_collect_bilibili_single` 都用 `next((t for t in index if t.get("title") == title), None)` 决定「更新已有」还是「新建」。后果：

- 两个主题起同一显示标题 → 后采的写进前者；
- 标题改过之后再用原关键词重采 → 新建重复单元；
- 同一批链接换个标题再粘 → 同一内容两个单元。

**建议**：id 与显示标题解耦（关键词/链接集合算稳定哈希，或要求显式 `--id`），标题只做展示；`update_title` 之后仍应能靠原 input 命中同一单元。

## 五、P2 / P3：工程质量

1. **采集函数重复**：`collect_topic` / `_collect_bilibili_single` / `_collect_article_single` / `collect_batch` 的「id 解析 → merge → unchanged 判定 → attach_intake → save → 日志」五份高度雷同，且已分叉（batch 可产出 `type=single`，topic 永远 `series`）。抽一个 `_finalize_unit(...)` 收益最高。
2. **零测试零 CI**：三个网页解析器（百度 `c-result`、360 `res-list`、小红书 `__INITIAL_STATE__`）完全依赖对方 DOM，任何一方改版都静默失效，目前验证方式只有人工跑一遍。建议把抓回的样本页存成 fixtures，做离线解析回归；再加一条 CLI `--dry-run` 冒烟。
3. **死参数 / 死代码**：`min_match`、`match_all` 从 CLI → server → `pick_series` → `title_match` 全链路传递，但 `title_match` 只做 `keyword in title`，参数完全不生效，对外却暴露成可调选项。`LEGACY_DIR`（88 行）定义后从未使用。
4. **旧架构遗留**：`topics/*.html`（9 个）与 `assets/data/*.js`（9 个根数据文件）已确认无引用（页面只读 `assets/data/index.js` + `assets/data/collections/*.js`），仍在仓库里；TODO 已有条目但未执行。
5. **缓存策略一刀切**：`end_headers` 对所有响应加 `no-store`，包括 `style.css` 与封面图。建议只对 `*.html`、`assets/data/*.js` 禁缓存，静态资源给短缓存。
6. **双写事实**：`enabled` 同时写 index 与单元文件；`count` / `updated` / `latest` 在索引与数据文件都存。当前一致（11 个单元一一对应，`count` 全部等于 `len(videos)`，已脚本校验），但 `set_enabled`、`record_intake_only` 各写一部分，长期易漂。
7. **错误静默**：`load_index` 解析失败返回 `[]`；`fetch_video_tags` 全部失败只 log。建议至少向 stderr 打明确告警，并让 `/api/health` 反映索引可读性。
8. **`/api/intake` id 未做白名单**（`server.py:121-155` 直接拼路径）。实测 `id=../../../README` 因非 `.js` 未成功，属低危；顺手加与前端 `safeId` 同款校验即可。
9. **`intake.input` 截断 8000 字符**：批量粘贴超长链接列表时，下次「重新采集」回填会不完整（`normalize_intake`）。
10. **工作区卫生**：`.playwright-cli/` 为新增未跟踪目录（建议加 `.gitignore` 或清理）；`.workbuddy/` 已被忽略，正常。

## 六、做得好的地方（建议保留）

- 纯标准库、无第三方依赖，部署成本极低；`Dockerfile` 对 `TZ` + `tzdata` 的处理是对的。
- 「采集只写数据、页面是固定模板」这条边界守得干净，页面样式各自内联，改版互不影响。
- 单元独立文件 + `enabled` 开关 + `runs` / `intake` 回填的设计很实用，重新采集不必重贴链接。
- `merge_videos` 的「旧有保留、新数据覆盖、无变化不写盘」逻辑正确，报告口径（新增/更新/未变/合计）清楚。
- `backup_data.py` 还原时的路径穿越拦截（拒绝绝对路径与 `..`）比多数同类脚本严谨，且还原前自动留快照。
